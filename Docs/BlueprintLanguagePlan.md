### 현재 구현의 경계

- 정수는 0 이상 Int32, 변수 대입/참조, 주석, 숫자 함수 1~4, 완성품 판정 !만 실행된다. 음수·계산식·중첩 호출·조건·반복·사용자 함수·컬렉션·난수는 미구현이다.
- Evaluate는 줄을 Trim하고 첫 = 및 정규식 호출을 검사한다. 1차 구조/타입 검사와 2차 상태 평가 모두 선형 순회다. 이 구조에 if를 단순 추가하면 실행하지 않을 분기까지 상태를 바꾸거나 검사할 위험이 있다.
- Piece에는 heat와 shaped만 있다. 1은 철만, 4는 공기만 허용한다. 5번 장착, 물 담금질, 경도, 속성별 가격은 없다.
- Execute(true)는 평가 결과만 보여 준다. Execute(false)는 성공 공정 목록을 Craft로 재생한다. Craft가 자금·철을 확인하고 성공 단계 비용을 차감하며, 이전 소비는 실패해도 남긴다. 현재 평가기는 실제 자금/철 부족을 시험 결과에 반영하지 않는다.
- 실제 제작은 단일 busy 잠금이며 코드 변경·창 전환과 분리된 결과를 재생한다. 판매는 FIFO 항목을 제거하고 28G를 지급한다.
- 여러 코드 창은 독립 소스/undo/스크롤을 갖는다. f1 같은 창 이름은 사용자 함수 정의가 아니다. 코드 색상과 툴팁은 표시 기능이며 예약어에 색상이 있어도 실행 지원을 뜻하지 않는다.
- 기존 검증 기록에는 C# 컴파일·단위 비교 결과가 있으나 Play Mode 편집/IME/스크롤 검증은 남아 있다. 본 문서의 예제 검토를 새 언어 구현 통과로 기록하지 않는다.

## 2. 호환성과 문법 방향

### 2.1 반드시 유지할 기본 도면

```text
Material = 1
Blade = 1(Material)
2(Blade, 7)
3(Blade)
4(Blade, 0)
!Blade
```

수용 기준: 철 1개, 제작비 12G, 열 0·성형 완료인 철 검날 1개, 판매가 28G, 순이익 16G. 초기 자금100/철10에서 실제 제작 후 88/9/완성품1, 판매 후 116/9/완성품0. 시험만 실행하면 실제 자금100/철10/완성품0 및 3D 작업물이 그대로다. 주석·빈 줄·한글 변수명으로 바꾸어도 같은 의미다. 함수 1의 결과는 이름에 저장해야 하고 함수 2~4에는 반환값이 없다.

### 2.2 기존 제안과의 충돌 처리

| 항목 | 현재 구현 여부 | 권장 문법 | 기존 도면에 미치는 영향 |
|---|---|---|---|
| 숫자 공정 1~4 | 구현 | 그대로 유지 | 위 기본 도면 수정 없음 |
| !Blade | 구현 | 모듈 본문의 완성품 판정으로 유지 | return과 의미가 다름. 기존 판정 후 명령 금지 유지 |
| PDF의 ? 조건: | 미구현 후보 | if 조건: / else: | 실행된 기존 문법이 아니므로 변환 대상은 PDF 예시뿐. ?에는 “if를 사용하세요” 오류, 별칭은 추가하지 않음 |
| PDF의 +, >= | 미구현 | 정수 산술·비교 연산으로 채택 | 과거 정상 도면에 영향 없음 |
| PDF의 10(DragonBone + 4) | 미구현 절댓값 후보 | abs(DragonBone + 4) | 10을 절댓값으로 예약하지 않음. 미지원 10 호출에 abs 안내. 미래의 공정 번호와 충돌 방지 |
| >, >> 등의 가속 표기 | 미구현 후보 | >는 비교, >> 계열은 첫 버전 미지원 | 가속은 이후 상점/실행 설정으로 설계. 같은 기호를 두 의미로 사용하지 않음 |
| 열 단계 조회 | 미구현 | heat(Blade) | 읽기 전용 계산 기능이므로 이름 사용, 상태를 바꾸는 공정은 숫자 유지 |
| Python 변수명·예약어 | 구현 | 기존 이름 검증을 유지 | 이미 금지된 if/def 등을 문법으로 활성화. match/case/type은 계속 일반 변수 |
| 이름 내장 함수 | 미구현 | abs/len/min/max/heat/random/set | 기존 abs = 1 같은 도면을 깨지 않도록 값 이름과 호출 이름의 공간을 분리 |
| 물·손잡이·별철 | 미구현 | 4(Blade, 3), 5(Blade, 2) 등 별도 공정 확장 | 언어 확장만으로 해금하지 않는다. 공정 레지스트리에 등록되기 전에는 미지원 오류 |

새 소스는 언어 버전 v2로 컴파일한다. 기존 유효 v1 소스는 v2의 부분집합으로 수용한다. 숫자 호출은 정수 리터럴 바로 뒤의 괄호로 구분하며 1(1)은 일반 정수를 함수처럼 호출하는 기능이 아니다. 현재 파서가 받아들이는 선행 0 표기(01(1), 007)도 10진수로 유지한다. 함수 번호를 변수에 넣어 호출하거나 함수 자체를 값으로 전달하는 기능은 없다.

### 2.3 첫 확장 버전의 공통 규칙

- Python 전체를 실행하지 않는다. Python과 유사한 문법을 가진 게임 전용 언어이며 import/eval/파일·네트워크 접근은 없다.
- 한 논리 문장은 한 줄. 세미콜론, 한 줄 if, 여러 줄 괄호 이어쓰기, 문자열, 실수, 컴프리헨션, lambda, 예외 처리, 클래스는 제외한다. #부터 줄 끝은 주석이다.
- 블록 머리에 :를 쓰고 공백 4개씩 들여쓴다. 빈 줄·주석 전용 줄은 블록 깊이에 영향이 없다. 탭은 문법 오류이며 편집창 Tab 키는 공백 4개를 입력한다. 붙여넣은 탭을 자동으로 의미 변경하지 않고 변환 안내를 준다.
- 호환용으로 블록이 전혀 없는 기존 선형 도면은 각 줄의 선행 공백을 무시한다. if/for/while/def/else가 하나라도 있으면 전체 소스에 엄격한 들여쓰기 규칙을 적용한다. 이 예외는 v1에서 Trim으로 허용하던 도면을 보존하기 위한 것이다.
- 값 종류: Int32 정수, bool(True/False), None, 작업물 참조, 아래에서 제한한 컬렉션. bool은 정수로 취급하지 않는다. 변수는 타입 선언 없이 대입하며 다른 타입으로 재대입할 수 있다. 연산 직전 실제 타입을 검사한다.
- 음수와 단항 -를 추가한다. +, -, *, //, %는 정수 전용이며 //는 내림 나눗셈, %는 그 규칙에 맞는 나머지다. /와 거듭제곱은 제외한다. 0 나누기, 범위 초과, abs(-2147483648)는 오류이고 자동 래핑하지 않는다. -2147483648 리터럴은 허용한다.
- 우선순위(높음→낮음): 호출·인덱스, 단항 -, * // %, + -, 비교·in, not, and, or. and/or는 단락 평가한다. 조건과 논리 연산은 bool만 허용한다. if 1:은 오류다.
- < <= > >=는 정수끼리만, == !=는 같은 스칼라 타입/작업물 동일 참조 또는 None 확인에만 허용한다. 값 == None은 값 종류와 무관하게 허용한다. 컬렉션 전체 비교와 a < b < c 연쇄 비교는 제외하며 and로 풀어 쓴다.
- 표현식의 인자와 컬렉션 원소는 왼쪽부터 평가한다. 일반 계산·조회·사용자 함수의 중첩 호출은 허용한다. 상태 변경 숫자 호출은 별도 문장(1은 이름 대입)에서만 쓴다. 2(1(1), 7)은 오류, 2(Blade, min([7, 9]))는 허용한다.
- if/for/while는 새 변수 스코프를 만들지 않는다. def만 지역 스코프를 만든다. 읽기 전에 모든 도달 가능한 경로에서 대입되었는지 검사하며, 판단할 수 없는 동적 타입/값은 런타임 검사한다.
- 정의/대입/인자 이름은 기존 PythonIdentifier 규칙을 사용한다. 값 변수 abs와 호출 abs(...)는 별개이므로 abs = 1은 유효하다. 사용자 함수가 내장 호출 이름을 덮어쓰거나 같은 이름으로 두 번 정의되는 것은 오류다. 이름 비교는 NFKC 정규화 후 수행한다.

## 3. 기능별 명세

아래 예시는 별도 표시가 없으면 문법 설명용 조각이다. 독립 제작 도면은 4절을 사용한다. 공정 관련 예시는 아직 미구현인 물·장착에 의존하지 않는다.

### 3.1 조건문, 비교, 상태 조회

| 기능 | 사용 문법·입력 | 반환/동작 | 게임 예시 | 오류 예시 |
|---|---|---|---|---|
| 조건 분기 | if bool식: 블록 / 선택적인 else: 블록 | 참/거짓 중 한 블록만 실행, 문장 반환값 없음 | if heat(Blade) < 6: 아래에서 2(Blade, 7) 호출 | if 7: → bool 필요; else 단독 → 대응 if 없음 |
| 비교 | a <= b, a == b 등 | bool | target >= 6 and target <= 9 | Blade < 7 → 정수 비교 필요 |
| 상태 조회 | heat(piece) | 그 시점의 작업물 열 단계 Int32, 0~9 | current = heat(Blade) | heat(1), heat() → 작업물 1개 필요 |

heat는 마지막으로 성공한 공정 이후의 논리 상태를 읽는다. 무료이고 상태·연료·시간을 바꾸지 않는다. 렌더러 색상이나 실시간 경과로 온도를 추측하지 않는다. 현재 게임은 자연 냉각이 없으므로 while heat(Blade) > 0:만 반복해도 식지 않는다. 향후 자연 냉각/대기는 명시적인 공정과 논리 시간 규칙으로 추가해야 시험·실제 결과가 일치한다.

```text
Blade = 1(1)
if heat(Blade) < 6:
    2(Blade, 7)
else:
    2(Blade, 6)
3(Blade)
4(Blade, 0)
!Blade
```

새 작업물의 heat는 0이라 첫 분기만 실행한다. else 검증은 분기 전에 2(Blade, 8)을 추가한 변형으로 한다. 첫 버전에는 elif를 넣지 않고 else 안에 if를 중첩한다.

### 3.2 반복문과 break

| 기능 | 사용 문법·입력 | 반환/동작 | 게임 예시 | 오류 예시 |
|---|---|---|---|---|
| for | for candidate in candidates: | list[int]를 순서대로 순회. 4단계 이후 tuple[int]도 허용. 문장 반환값 없음 | [9, 7, 5]에서 첫 적합값 선택 | for x in 7: → 리스트/튜플 필요 |
| while | while bool식: | 매 반복 전 조건 재평가. False면 0회도 가능 | 시도 횟수를 3으로 제한하여 후보 생성 | while 1: → bool 필요 |
| break | 반복문 내부의 독립 문장 | 현재 함수 안에서 가장 가까운 for/while만 종료 | 적합값 저장 후 break | 반복문 밖 또는 반복문이 호출한 함수 안의 단독 break → 오류 |

for의 입력은 진입 시 한 번 평가하고 원소 스냅샷으로 순회한다. 반복 중 원본 리스트 인덱스를 바꿔도 이번 순회 후보는 변하지 않는다. 빈 리스트는 0회이며 for 변수는 새로 생기지 않는다. 따라서 반복 밖에서 사용할 값은 먼저 초기화한다. break는 바깥 반복이나 도면 전체를 종료하지 않는다. continue, for/while의 else, range는 첫 버전에서 제외한다.

```text
attempts = 0
while attempts < 3:
    attempts = attempts + 1
    if attempts == 2:
        break
```

결과는 attempts == 2. 계산 반복에는 제작비가 없지만 실행 예산은 소비한다.

### 3.3 사용자 함수

| 항목 | 권장 규칙 |
|---|---|
| 선언/호출 | def choose(candidates, limit): / result = choose([9, 7, 5], 7). def는 들여쓰기 0의 최상위에서만 선언하며 모듈 전체에서 먼저 이름/인자 수를 수집하므로 정의보다 앞선 호출도 허용한다. |
| 입력 | 위치 인자만, 최대 8개. 기본값, 가변 인자, 키워드 인자, 함수 값, 중첩 def, 클로저는 제외한다. |
| 지역 변수 | 인자와 함수 내 대입은 지역 변수. 모듈 변수는 암묵적으로 읽거나 쓰지 못하며 필요한 값을 인자로 넘긴다. 내장·사용자 함수 호출 이름은 공유한다. global/nonlocal은 제외한다. |
| 반환 | return 식, return, 함수 끝 도달. 뒤의 두 경우 None. 값 있는 return은 스칼라/작업물/허용 컬렉션을 반환한다. return은 해당 함수만 끝내며 판매 완료를 뜻하지 않는다. |
| 공정 호출 | 허용한다. 작업물 인자를 받은 함수에서 2~4를 실행하면 같은 작업물에 영향을 준다. 1로 생성한 작업물도 반환 가능하다. 공정 부작용은 호출한 함수의 숨은 무료 작업이 아니라 일반 제작 원장에 기록한다. |
| 참조/복사 | 작업물만 동일 ID의 공유 참조. 리스트·딕셔너리·집합·튜플은 값 의미로 복사(대입·인자·반환)한다. 함수에서 바꾼 컬렉션을 쓰려면 return하여 다시 대입한다. 첫 버전의 중첩 컬렉션 금지가 복사 비용을 제한한다. |
| 재귀 | 직접·간접 재귀 모두 미지원. 정적 호출 그래프의 순환을 컴파일 오류로 막는다. 비재귀 긴 호출 체인도 최대 32개 활성 프레임 제한을 받는다. |
| 완료 판정 | 함수 안의 !는 금지. 완성품은 호출자에게 반환하고 모듈 본문에서 !로 판정한다. |

```text
def heat_to(piece, target):
    2(piece, target)
    return heat(piece)

Blade = 1(1)
actual = heat_to(Blade, 7)
3(Blade)
4(Blade, 0)
!Blade
```

actual은 7이고 가열은 1회다. 오류 예: heat_to(Blade)는 인자 수 부족, return 7은 최상위에서 사용 불가, 지역 변수 actual을 함수 밖에서 읽으면 미정의 이름, def f(): 안의 f()는 재귀 오류다. 공정 함수를 조건식 안에서 숨겨 호출하는 것을 줄이기 위해 **공정을 직접/간접 호출하는 사용자 함수는 독립 호출문 또는 단순 이름 대입의 우변 전체에서만 허용**한다. if heat_to(Blade, 7) > 0:은 “공정 포함 함수를 먼저 별도 줄에서 호출하세요” 오류다. choose 같은 순수 함수는 계산식 어디서나 호출할 수 있다.

### 3.4 컬렉션

첫 버전의 컬렉션은 최대 1,024개 원소이며 정수만 담는다. 작업물·컬렉션 중첩·bool 원소는 허용하지 않는다. 재료 번호도 정수이며 자료구조에 3을 저장했다고 물 공정이 해금되지는 않는다.

| 기능 | 사용 문법·입력 | 반환·변경 규칙 | 게임 예시 | 오류 예시 |
|---|---|---|---|---|
| 리스트 | [9, 7, 5], [], values[i] | 순서 유지. 0 기반 정수 인덱스. values[i] = n만 변경 허용. append/삭제/슬라이스/이어붙이기는 제외 | candidates[1] → 7 | candidates[3], candidates[-1] → 범위 오류; candidates[0] = True → 정수 필요 |
| 딕셔너리 | {1: 2, 3: 1}, {}, stock[key] | int 키→int 값. stock[key] = n으로 기존 값 변경/새 키 추가. 없는 키 읽기는 오류. 리터럴 중복 키는 평가 후 마지막 값 우선 | stock[1] = stock[1] - 1 | stock[2] → 키 없음; stock[True] → 정수 키 필요 |
| 집합 | {0, 3}, set() | 정수 중복 제거. int in set은 bool. 첫 버전은 원소 추가/삭제 없이 변수 전체 재대입만 허용. 순회/인덱스 제외 | 0 in {0, 0, 3} → True, len → 2 | allowed[0] → 인덱스 미지원; set(3) → 인자 없는 생성자만 허용 |
| 튜플 | (6, 9), (7,), (), limits[i] | 순서 있는 불변 정수 묶음. 0 기반 접근. (7)은 괄호 계산식이고 (7,)이 튜플. 언패킹 제외 | limits[0] → 6 | limits[0] = 7 → 변경 불가; limits[2] → 범위 오류 |

in은 list/tuple/set의 원소 및 dict의 키에 대해 허용한다. 왼쪽은 정수이며 반환은 bool. 3 in 7은 오류다. 빈 {}는 dict, 빈 set은 반드시 set()이다. 자료구조의 수량은 플레이어의 계획 데이터이며 실제 재고와 자동 연동하지 않는다. stock[1] = 999로 실제 철을 늘릴 수 없다. 딕셔너리 값 자체는 음수도 저장할 수 있으나 수량을 나타내는 예제에서는 0 이상 여부를 조건으로 검사한다.

### 3.5 내장 함수

| 함수 | 입력과 반환 | 게임 용도·정상 예 | 잘못된 입력 처리 |
|---|---|---|---|
| abs(n) | 정수 1개 → 정수 | abs(5 - 7) → 2, 온도 차이 | abs(), abs(Blade), abs(-2147483648)는 각각 인자/타입/범위 오류 |
| len(values) | list/dict/set/tuple 1개 → 정수 | len([9, 7, 5]) → 3, len({}) → 0 | len(7), len(a, b)는 오류 |
| min(values) | 비어 있지 않은 list[int]/tuple[int] 1개 → 정수 | min([9, 7, 5]) → 5 | min([]), min(()), min({1, 2}), min(1, 2)는 오류 |
| max(values) | min과 동일 → 정수 | max((6, 9)) → 9 | 빈 목록·dict/set·혼합형·다중 인자는 오류 |
| random(low, high) | 정수 2개, low <= high → 양 끝 포함 정수 | random(1, 7)는 1~7 후보, random(7, 7)는 항상 7 | random(7, 1), random(1), random(True, 7)는 오류 |
| heat(piece) | 살아 있는 현재 실행의 작업물 1개 → 정수 | heat(Blade) → 마지막 성공 공정 후 열 단계 | 숫자/None/이전 실행의 참조는 오류 |
| set() | 인자 없음 → 빈 정수 집합 | allowed = set() | set([0, 3]) 변환 오버로드는 첫 버전 제외 |

min/max는 단일 컬렉션 형태로 통일한다. 두 값을 비교할 때도 min([a, b])를 사용한다. 내장 함수 실패는 값을 반환하지 않으며 호출 줄에서 실행을 멈춘다. 값이 정적으로 확정된 잘못된 인자는 제작 시작 전 오류로 보고하고, 실행 중 계산으로 결정되는 경우에는 해당 호출 시 검사한다.

**인자 없는 random() 결정안:** 첫 버전 미지원. 0~1 실수는 정수 기반 열 단계/재료 번호와 맞지 않고, 임의의 기본 정수 범위도 용도를 숨긴다. 확률이 필요하면 random(1, 100) <= 25를 사용한다. 실수형을 도입하는 후속 버전에서만 별도 검토한다. random은 제어 흐름을 바꿀 수 있으므로 순수 상수 접기 대상으로 취급하지 않는다.

## 4. 실제 제작 도면과 데이터 예제

### 4.1 후보를 선택한 뒤 한 번만 가열하는 완성 도면

```text
def choose_heat(candidates, limit):
    selected = None
    for candidate in candidates:
        if candidate <= limit:
            selected = candidate
            break
    return selected

Candidates = [9, 7, 5]
Limit = 7
Target = choose_heat(Candidates, Limit)
if Target != None:
    if Target >= 6 and Target <= 9:
        Material = 1
        Blade = 1(Material)
        2(Blade, Target)
        3(Blade)
        4(Blade, 0)
        !Blade
```

| 진행 | 기대 결과 |
|---|---|
| 9 검사 | 9 <= 7은 False, 공정 실행 없음 |
| 7 검사 | True, selected에 7 저장, break로 for 종료 |
| 5 | 검사하지 않음 |
| 함수 반환 | 7 반환. 후보 루프에는 가열 호출이 없음 |
| 제작 | 1 → 2(열 7) → 3 → 4(공기) → ! 순서. 2 호출 정확히 1회 |
| 경제 | 철1, 비용12G, 판매28G, 이익16G |
| Candidates = [9, 8] 또는 [] | None 반환. 1조차 실행하지 않고 “조건 불충족으로 제작 건너뜀 · 비용 0G”. 완성품 없음 |
| Candidates = [5, 7] | 첫 조건 적합값은 5. 추가 제작 가능 범위 검사에서 건너뜀. 임의로 다음 후보 7을 다시 찾지 않음 |

선택 조건 “제한값 이하의 첫 후보”와 공정 조건 “타격 가능한 열 6~9”를 분리했다. 적합 후보가 없을 때 실패 작업물을 먼저 생성하지 않는 것이 핵심이다.

### 4.2 딕셔너리로 계획 수량 기록

```text
Stock = {1: 2, 3: 1}
if 1 in Stock:
    if Stock[1] > 0:
        Blade = 1(1)
        Stock[1] = Stock[1] - 1
        2(Blade, 7)
        3(Blade)
        4(Blade, 0)
        !Blade
```

Stock[1]은 1이 된다. 실제 철 재고는 1 호출에서 별도로 확인·차감한다. 3:1은 물의 계획 수량일 뿐 이 예제는 물을 쓰지 않는다. 키가 없거나 계획 수량이 0이면 공정 없이 건너뛴다.

### 4.3 집합으로 냉각 재료 검사

```text
AllowedCoolants = {0}
Coolant = 0
if Coolant in AllowedCoolants:
    Blade = 1(1)
    2(Blade, 7)
    3(Blade)
    4(Blade, Coolant)
    !Blade
```

현재 구현된 공기만 허용한 예제다. 물 냉각 공정이 구현된 이후에만 {0, 3}으로 확장한다. 집합에 3을 추가하는 것 자체는 유효한 자료구조 표현이지만 4(Blade, 3)의 실행 지원을 의미하지 않는다.

### 4.4 튜플과 내장 함수로 기준 계산

```text
Limits = (6, 9)
Desired = 10
Target = min([Limits[1], max([Limits[0], Desired])])
Difference = abs(Target - Desired)
CandidateCount = len([9, 7, 5])
Blade = 1(1)
2(Blade, Target)
3(Blade)
4(Blade, 0)
!Blade
```

Target=9, Difference=1, CandidateCount=3. min/max 오버로드를 늘리지 않고 목록 형태로 범위를 제한한다.

### 4.5 while·난수 검증용 완성 도면

```text
Attempts = 0
Target = None
while Attempts < 3:
    Candidate = random(1, 7)
    Attempts = Attempts + 1
    if Candidate >= 6:
        Target = Candidate
        break
if Target != None:
    Blade = 1(1)
    2(Blade, Target)
    3(Blade)
    4(Blade, 0)
    !Blade
```

최대 3번 추첨하고 6 또는 7을 찾았을 때만 실제 공정을 시작한다. 실패하면 비용0/완성품0이다. 실제 제작을 시작하지 않은 시도만 반복해서 난수를 바꾸지 못하도록 6.4절의 시드 슬롯 규칙을 적용한다.

## 5. 코드 창, 툴팁, 오류 표시

### 5.1 편집 지원

CodeWindow의 원문·스크롤·undo·색상 캐시 구조와 독립 창 동작을 유지한다. Tab/Shift+Tab은 선택 줄의 4칸 들여쓰기/내어쓰기를 하나의 undo 이벤트로 처리하고, Enter는 현재 들여쓰기를 유지하며 블록 머리의 : 뒤에서는 4칸을 추가한다. 실제 원문에는 색상 태그를 넣지 않는다. 창 이름을 def 이름으로 자동 연결하지 않는다. 첫 버전 함수는 실행한 창의 소스 안에서만 찾으며 다른 창의 정의는 가져오지 않는다.

구문 강조는 공통 토큰/구문 정보를 사용한다. 주석 초록, 변수 흰색, 공정 재료 위치의 숫자 핑크, 지원 제어 예약어·True/False/None·! 주황, 숫자 공정 및 이름 호출의 함수명 연노랑을 유지한다. 일반 정수/난수 경계/열 단계는 흰색이다. 사용자 함수 매개변수 이름만으로 재료라고 추측하지 않는다. 미정의 함수는 연노랑 표시와 별개로 오류 밑줄을 준다.

### 5.2 문맥 툴팁

| 대상 | 표시 내용 |
|---|---|
| 2(Blade, 7)의 2 | 가열 · 입력: 작업물, 목표 열 단계 · 연료2G |
| 같은 호출의 7 | 목표 열 단계 · 7 · 허용1~9 |
| random(1, 7)의 7 | 난수 범위의 최댓값 · 7 포함 |
| random(1, 7)의 1 | 난수 범위의 최솟값 · 1 포함 |
| 2(Blade, random(1, 7))의 7 | 직접 부모인 random의 최댓값을 우선. 보조 설명 “결과가 가열 목표 열 단계로 전달됨” |
| 4(Blade, 0)의 0 | 냉각 재료 · 공기 · 비용0G |
| heat(Blade)의 Blade | 작업물 인자 · 최근 실행 스냅샷의 열 단계가 있으면 값/실행 ID 함께 표시 |
| choose_heat(Candidates, 7)의 7 | choose_heat의 2번째 매개변수 limit. 자동으로 재료 번호라고 하지 않음 |
| [9, 7, 5]의 7 | 정수 원소 · 인덱스1 |
| 주석 안의 숫자 | 툴팁 없음 |

Describe의 줄별 괄호 정규식을 호출 AST의 범위·매개변수 정보로 교체한다. 숫자 토큰의 가장 안쪽 호출과 인자 위치를 사용하므로 중첩 괄호/리스트의 쉼표를 인자 구분으로 오해하지 않는다. 입력 중 불완전한 줄은 복구 가능한 부분 AST를 사용하고 불명확하면 “정수 값”만 표시한다. 툴팁 계산 때문에 사용자 함수를 실행하거나 난수를 소비하지 않는다. 0.5초 대기와 편집·이동·스크롤 시 숨김은 유지한다.

### 5.3 오류 위치와 분류

원문 기준 1부터 시작하는 줄/열, 창 ID와 실행 소스 버전, 함수 호출 스택을 보관한다. 탭 변환이나 NFKC 정규화로 원문 위치를 잃지 않도록 토큰의 UTF-16 시작/길이와 사용자 표시 열을 별도로 관리한다. 메시지 예시는 아래의 해당 줄 n을 사용한다.

| 문제 | 표시 줄 | 메시지·시점 |
|---|---|---|
| if 머리 다음 줄이 2칸 들여쓰기 | 잘못 들여쓴 본문 줄 n | 컴파일 오류 · n줄: 들여쓰기는 공백4칸 단위입니다 |
| if 뒤 본문 누락 | 다음 유효 줄, EOF이면 if 줄 | 컴파일 오류: if 블록의 본문이 필요합니다 |
| 반복문 밖 break | break 줄 | 컴파일 오류: break는 현재 함수의 반복문 안에서만 사용할 수 있습니다 |
| unknown(7) | 호출 줄의 unknown | 컴파일 오류: 정의되지 않은 함수 unknown |
| random(1), 2(Blade) | 호출 줄 | 컴파일 오류: random/2에 인자2개가 필요합니다 |
| 실행 중 Target가 None인데 2에 전달 | 2 호출 줄의 Target | 실행 오류: 목표 열 단계는 정수여야 합니다 · 받은 값 None |
| Stock[3], 키3 없음 | 대괄호 접근 줄 | 실행 오류: 재료 수량 표에 키3이 없습니다 · in으로 존재 여부를 확인하세요 |
| 리스트 범위 밖 | 인덱스 접근 줄 | 실행 오류: 인덱스3은 범위 밖입니다 · 길이3, 허용0~2 |
| 분기에서만 대입 후 무조건 읽기 | 읽는 줄 | 컴파일 오류: Target가 모든 경로에서 대입되지 않았습니다 |
| 재귀 호출 | 순환을 닫는 호출 줄 | 컴파일 오류: 재귀 호출은 지원하지 않습니다 · f → g → f |
| 명령 수/호출 깊이 초과 | 6.3절의 다음 실행 위치 | 실행 제한: 명령 수10000 또는 호출 깊이32 초과 |
| 낮은 열에서 타격 | 3 호출 줄 | 공정 오류: 타격에는 열 단계6 이상이 필요합니다 · 현재5 |

함수 내부 오류는 정의 본문 줄을 주 위치로, 호출자 줄을 스택으로 표시한다. 실행 중 원문이 편집되면 현재 편집본의 잘못된 줄을 강조하지 않고 실행 당시 소스를 결과 창에서 보여 준다. 현재의 “steps.Count == 0이면 컴파일 오류” 추정은 폐기하고 DiagnosticKind(구문/이름/타입/공정/실행제한), SourceSpan, CallStack을 명시적으로 전달한다. 선택되지 않은 분기도 구문·함수 이름·고정 인자 수는 검사하지만 상태 변경·난수·실제 컬렉션 접근은 하지 않는다.

## 6. 실행 모델과 자원 보존

### 6.1 선행 구조 변경

권장 흐름은 원문 → 공통 lexer(INDENT/DEDENT 포함) → AST → 이름/제어 구조/검증 → 실행 계획 평가 → 성공 공정 재생이다. 게임잼에서는 원본 위치를 가진 AST 인터프리터로 시작하고, 바이트코드 VM은 후속 최적화로 둔다. PDF의 바이트코드 방향을 버리는 것이 아니라 반복 제어에 필요한 의미를 먼저 고정한다.

- Evaluate의 1차 검사에서 실제 Piece를 변경하는 방식을 없앤다. 정적 검사는 심볼·정의 여부·제어 구조·알려진 타입만 다룬다. 2차는 선택된 분기와 반복만 실행한다.
- BuiltinRegistry에 숫자 공정과 이름 내장을 등록하고 인자 이름/타입/범위/비용/부작용 정보를 툴팁과 실행이 공유한다.
- Piece는 실행 내 고유 ID로 식별한다. 계획 상태와 화면 오브젝트를 분리하고 공정 이벤트에 대상 Piece ID 및 이전/이후 상태를 기록한다. 기존 단일 work 큐브에 모든 변수 대입까지 덮어 그리는 방식은 교체한다.
- 수량·자금도 계획의 초기 스냅샷에서 추적한다. 시험은 현재 보유 자원에서 어디까지 제작 가능한지 표시하되 복제 상태만 바꾼다. 이는 현재 시험 평가기에 없는 추가 기능이다.
- 이벤트는 변수/분기 기록과 비용 있는 공정을 분리한다. 계산 한 줄마다 현재 Craft처럼 0.65초씩 기다리지 않는다. 기존 공정의 대기0.65초는 유지하고 계산은 프레임별 예산 안에서 진행한다. 기본 도면의 결과·비용 호환이 필수이며 현재 모든 Step에 붙는 대기시간 자체는 호환 계약에 포함하지 않는다.
- 계획 평가 중에도 busy 잠금을 먼저 설정하고 프레임당 실행량 제한을 적용한다. 실제 제작 준비부터 재생 종료까지 공방 자원 변경/판매/다른 실행을 막는다. 소스 편집과 창 전환은 계속 허용한다.

### 6.2 성공·건너뜀·실패

**!와 return:** !는 모듈 본문 또는 그 if/else 안에서만 허용하고, for/while/def 안에서는 금지한다. 실행당 완성품1개를 확정하고 실행 전체를 끝낸다. 같은 블록에서 무조건 ! 뒤에 명령을 쓰는 것은 기존처럼 컴파일 오류다. 함수 return은 호출자에게 값을 돌려줄 뿐 완성품·판매 재고를 만들지 않는다.

**도면 끝:** 소스의 모듈 실행부에 !가 하나도 없으면 기존 “완성품 반환이 필요합니다” 컴파일 오류를 유지한다. !가 조건 분기에 있지만 해당 경로가 선택되지 않은 경우, 성공한 숫자 공정이 0개면 “제작 건너뜀”으로 정상 종료한다. 숫자 공정을 하나라도 실행하고 ! 없이 끝나면 “완성품 반환 없이 종료” 실행 오류이며 이전 공정 소비가 남는다. 4절 후보 없음 예제가 전자의 경우다. 제작과 무관한 문법 조각 테스트는 인터프리터 테스트 하네스에서 하고 게임 도면 완료로 처리하지 않는다.

**자원 원칙:**

1. 컴파일 오류는 전체 도면 시작 전 중단, 비용0/재고 변화0이다.
2. 계획 평가의 공정·값·실행 제한 오류는 오류 직전 성공 이벤트를 보존한다. 실제 실행 버튼을 누른 경우 이 접두 공정을 재생한 뒤 오류 위치에서 종료한다. 미리 평가하다 실패했다는 이유로 이미 의미상 수행한 공정을 무료로 돌려주지 않는다.
3. 각 공정은 상태·인자·자원을 모두 확인한 뒤 비용/재고/작업물 상태를 한 번에 확정한다. 실패한 공정은 일부만 소비하지 않는다. 실제 재생에서도 방어적으로 재검사한다.
4. 이미 확정한 비용과 마지막 성공 작업물은 유지한다. 자동 환불·복구는 없다. 실패 작업물 재개/회수/폐기는 기존 미결정 범위로 남긴다.
5. 성공 !에서만 완성품 큐에1개를 넣는다. 기본 철 검날 가격28G와 기존 FIFO 판매 원칙을 유지한다. 판매 영수증에는 실제 확정된 원장의 비용을 쓴다.
6. 실행 중 취소도 공정 경계에서 처리하며 확정된 공정은 유지한다. 순수 계산 중 취소했다면 공정0/비용0일 수 있다.

예: 1로 철을 올리고 가열까지 성공한 뒤 무한 반복에 빠지면 실제 제작은 철1/12G를 소비하고 뜨거운 작업물을 남기며 완성품0이다. 시험에서는 같은 예상 소비·중단 위치를 보여 주고 실제 자원은 그대로다. 실제 소모와 예정 비용을 결과 창에서 구분한다.

### 6.3 실행 제한 제안

| 제한 | 초기값 | 카운트/중단 규칙 |
|---|---|---|
| 총 실행 명령 수 | 10,000 | AST의 문장 진입·표현식 평가·반복의 조건/다음 원소 검사 각각1단위. 함수 본문도 같은 실행의 예산 공유. 10,001번째 작업 시작 전에 중단 |
| 함수 호출 깊이 | 사용자 함수32프레임 | 최상위0. 33번째 호출의 호출 줄에서 진입 전에 중단. 내장 함수는 사용자 프레임을 추가하지 않으나 명령 예산은 소비 |
| 프레임당 평가량 | 최대256단위 | 초과 시 다음 Unity 프레임으로 양보. 총 예산 초기화 없음. 시험과 실제에 같은 규칙 |
| 컬렉션 | 각1,024원소, 실행 중 합계16,384원소 | 생성/복사/확장 직전에 검사. 값 복사도 크기와 예산에 포함 |
| 공정 이벤트 | 실행당1,000개 | 1,001번째 숫자 공정의 호출 줄에서 시작 전 중단 |
| 소스/구문 중첩 | UTF-8 64KiB / 32단계 | 컴파일 전에 크기 검사, 파싱 중 깊이 검사. 컴파일러 자체의 무한 재귀/메모리 폭증 방지 |

컬렉션 구성·복사·min/max·in 등 원소 수에 비례하는 작업은 원소당1단위를 추가한다. 단일 내장 작업은 필요한 단위를 먼저 예약하고 예산 부족이면 그 호출/연산 줄에서 상태 변경 없이 중단한다. random의 난수 후보 추출도 예산에 포함한다. 정확한 카운트는 VM 구현 최적화와 무관한 언어 비용표(v2)로 고정한다.

while의 반복 조건 평가에서 예산이 끝나면 while 머리 줄, 본문 실행 중이면 해당 본문 줄을 가리킨다. 호출 제한은 호출자 줄, 컬렉션 한도는 생성/대입 줄이다. 현재 반복 횟수·사용한 명령 수·호출 스택을 함께 표시한다. 프레임 수/애니메이션 시간은 명령 수에 영향을 주지 않는다.

### 6.4 시험 실행·실제 제작·난수 시드

권장안은 **같은 소스·초기 공방 상태·실행 시드·규칙 버전이면 시험과 실제 결과를 재현**하는 것이다. 시험은 복제된 변수/작업물/재고/자금/PRNG만 변경하며 실제 RNG 상태, 완성품 큐, 3D 오브젝트를 변경하지 않는다.

- 도면 창마다 다음 제작용 SeedSlot을 보관한다. 세션 기본 시드 + 변하지 않는 창ID + 제작 시도 번호를 안정적인 해시로 결합한 32비트 시드를 사용한다. string.GetHashCode나 프레임 시간, 전역 UnityEngine.Random은 사용하지 않는다.
- PRNG는 버전을 고정한 PCG32 구현을 권장한다. 경계 포함 매핑은 64비트 구간 크기와 rejection sampling을 사용한다. low/high가 Int32 전체 범위여도 오버플로하지 않고 같은 시드·호출 순서에 같은 결과를 낸다. low==high도 한 번의 추첨으로 취급해 소비 규칙을 고정한다.
- 같은 슬롯에서 반복 시험하면 같은 난수열이다. 코드 변경은 시험 결과를 무효화하지만 슬롯을 새로 뽑지 않는다. 공정 없이 건너뛰기/컴파일 오류/첫 공정 전 실패는 슬롯을 소비하지 않는다.
- 실제 제작에서 첫 숫자 공정이 성공 확정되는 순간 그 슬롯을 소비 처리한다. 이후 실패·중단해도 다음 실행은 새 슬롯이다. 재생 도중에는 시작 시드가 고정되며 다음 슬롯을 참조하지 않는다. “성공한 검만 시드 증가”로 두지 않아 실패 재시도 무료 추첨을 막는다.
- 시험 결과 티켓에는 창ID, 원문 해시(줄바꿈 LF 정규화), 초기 공방 상태 버전, 언어/공정/PRNG 버전, 시드, 예상 이벤트 요약을 저장한다. 창 이름 변경·이동·확대는 무효화 요인이 아니며 원문/자원/규칙 변경은 무효화한다.
- 실제 실행 시 유효한 티켓이 있으면 같은 시드와 같은 스냅샷에서 동일 엔진으로 계획을 평가해 재현한다. 실제 재생은 기록된 값을 사용하며 random을 다시 호출하지 않는다. 시험 없이 실행해도 현재 슬롯에서 시작한다.
- 시험 후 다른 창의 제작/판매로 공방 상태가 달라지면 “시험 이후 자원이 변경되어 현재 상태로 재평가합니다”를 표시한다. 이전 결과의 완전 재현을 보장하지 않고 현재 상태로 새 계획을 만든다. 같은 슬롯의 난수열 자체는 유지하되 분기 변화에 따른 소비 순서는 달라질 수 있다.
- 시드·슬롯 소비 여부·난수 호출 순번/줄은 실행 기록에 남긴다. 저장 기능 도입 시 세션 시드와 창ID/시도 번호도 함께 저장한다. 현재 저장/로드는 미구현이다.

검증은 고정 시드에서 시험2회와 실제1회의 난수열·분기·공정 목록을 비교하고, 시험이 실제 자원 및 다음 슬롯을 변경하지 않았음을 확인한다. 재생 속도·창 전환·실행 중 소스 편집은 시작된 난수열에 영향을 주지 않아야 한다.

### 단계 공통 확인 목록

- 정상 도면, 컴파일 오류 도면, 실행 중 실패 도면, 공정 없이 건너뛰는 도면을 각각 시험/실제 양쪽으로 검증한다.
- 통과 조건은 반환값뿐 아니라 공정 순서·횟수·비용·실제 자원·완성품 개수·오류 위치·시드 소비 여부를 함께 비교한다.

## 8. 게임잼 우선 범위와 개발 전 결정 항목

### 게임잼 우선 범위

선행0과 1~3단계를 첫 출시 범위로 권장한다. 기본 제작 호환, 열 조회·조건 분기, 후보 목록에서 첫 값 선택, break, 비재귀 사용자 함수, abs/len/min/max까지면 플레이어가 자신만의 열 선택/가열 방법을 작성할 수 있다. 실행 예산·깊이 제한·시험 격리는 이 범위부터 필수다. while과 random 단계까지 안전장치를 미루지 않는다.

다만 현재 모든 완성품은 같은 철 검날28G이므로 언어만 늘려서는 “판매와 발견”이 완성되지 않는다. 별도 공정 작업으로 물 담금질의 상태별 경도 효과, 나무 손잡이5번, 보너스별 영수증을 붙이는 것이 게임 재미의 우선 과제다. 이 문서는 그 공정의 밸런스를 확정하거나 이미 구현된 것으로 취급하지 않는다.

### 후속 범위

4~5단계의 데이터 구조·while·난수, 경도/부품 상태 조회, 바이트코드 VM, 도면 파일 저장/로드 및 시드 영속화, 다른 코드 창 함수 가져오기, 언패킹·range·리스트 증감·elif·자연 냉각은 후속으로 둔다. 재귀·실수·문자열·예외 처리·임의 Python 실행은 현재 요구를 충족하는 데 필요하지 않다.

### 개발 착수 전에 승인할 문법·정책

아래는 미정의 빈칸이 아니라 본문을 일관되게 작성하기 위해 선택한 기본안이다. 변경하면 예제와 완료 기준도 함께 수정한다.

| 결정 항목 | 본 문서 기본안 | 바꿀 때의 영향 |
|---|---|---|
| 제어 표기 | if/for/def와 콜론·4칸, ? 미지원 | 문서 예시·파서·편집기 들여쓰기 동시 수정 |
| 정수·조건 | signed Int32, 엄격 bool, None 후보 없음 | 음수/오버플로/분기 검사 계약 변경 |
| 이름 내장과 변수 충돌 | 값과 호출 이름 공간 분리 | 예약 이름으로 바꾸면 abs 같은 기존 변수 도면 마이그레이션 필요 |
| 컬렉션 범위 | 정수 평면 컬렉션, 값 복사, 리스트 인덱스/딕셔너리 키 대입만 변경 | 중첩·참조 공유·메서드 추가 시 비용/별칭 규칙 재설계 |
| 인덱스 | 0 이상만, 음수/슬라이스 제외 | Python과 동일한 음수 접근을 원하면 명세·오류 사례 수정 |
| 사용자 함수 | 공정 허용, 지역 스코프, 재귀 금지 | 전역/재귀 추가 시 검증·호출 예산 설계 확대 |
| 판정과 무작업 | !는 모듈/if만, 조건 미충족 공정0은 건너뜀 | 대량 제작·루프 ! 허용 시 제품 원장/가격/실패 보존 재설계 |
| 상태 조회 | heat(piece), 논리 상태 조회 | 숫자 조회를 원하면 번호표·툴팁·예제 변경 |
| 내장 오버로드 | min/max는 목록/튜플1개, random은 정수 경계2개만 | 인자 없는 random()은 실수 지원 여부와 함께 별도 결정 |
| 시험 난수 | 같은 슬롯 재현, 첫 성공 공정에서 슬롯 소비 | 매 시험 재추첨은 무료 난수 탐색과 재현성 문제를 수용해야 함 |
| 실행 제한 | 10000단위/깊이32/프레임256 | 초기값은 플레이 테스트로 조정하되 중단·비용 원칙은 유지 |

## 9. 문서 검토 상태

현재 코드와 문서의 지원 여부를 대조했고, 모든 새 예제는 위 v2 문법으로 작성했다. 4.1은 후보 선택과 가열을 분리했으며 후보 없음 경로에는 작업물 생성이 없다. 기본 도면 비용은 현재 코드의10G+2G+0G를 기준으로 계산했다. 신규 언어 실행기·UI·난수 구현은 이번 작업에 포함하지 않았으며, 단계별 완료 기준은 앞으로의 검증 요구사항이다.

문서 자체 검증: 코드 블록9개의 들여쓰기·구조를 확인했다. 숫자 호출과 !만 임시 Python 테스트 표기로 바꾸어 핵심 후보4가지와 컬렉션 제작 예제3개의 기대 흐름을 대조했으며, 원본 자료 링크6개가 실제 파일을 가리키는지 확인했다. 이는 예제의 논리 점검이며 게임의 신규 파서·실행기 검증이 아니다.
